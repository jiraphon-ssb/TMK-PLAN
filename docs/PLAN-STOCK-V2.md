## ระยะ 2–4 — ระบบสต็อกแบบสมุดเคลื่อนไหว (ยังไม่เริ่ม)

### ปัญหาของโมเดลปัจจุบัน ("หมุดล่าสุด − ที่ขายหลังหมุด")
| ปัญหา | ผล |
|---|---|
| PO รับเข้าเขียน "หมุดใหม่" ที่คำนวณฝั่ง browser (`buildReceiveAnchors` = คงเหลือ + ที่รับ) | read-modify-write บนข้อมูลเงิน — คงเหลือค้าง/มีคนขายแทรก = เลขผิดถูกอบไว้ถาวร |
| ไม่มีประวัติการเคลื่อนไหว | ตอบไม่ได้ว่า "ทำไมเหลือ 12" |
| ขายวันเดียวกับวันนับไม่ถูกหัก (`d <= after`) | นับเช้า ขายบ่าย → คงเหลือสูงเกินจริง |
| ออเดอร์ที่ import ย้อนหลัง | ถือว่า "นับรวมแล้ว" ทั้งที่ตอนนับยังไม่มีใบนั้น |
| key = `ลาย‖สี‖ไซซ์` (ข้อความ) | เปลี่ยนชื่อลาย = ประวัติหลุด |

### ตารางใหม่ `tmk_stock_moves` (append-only)
```
id · sku_key · product_code · design/color/size   ← เก็บทั้งรหัสและชื่อ ณ ตอนนั้น
kind   open | count | in | out | adjust | return
qty    signed (+ เข้า / − ออก)
moved_at · ref_type (po|order|count|manual) · ref_id · note · by · created_at
```

**คงเหลือ = หมุดนับล่าสุด + (รับเข้า/ปรับ หลังหมุด) − (ขาย หลังหมุด)**
= `ตั้งต้น + PO รับเข้า − Sale ขาย` ตามที่ต้องการ โดยยังคง "การนับจริง = ความจริงที่รีเซ็ตทุกอย่างก่อนหน้า"

**ยอดขายยังคำนวณจาก `tmk_mp_skus` เหมือนเดิม** ไม่ materialize เป็นแถว `out`
เพราะออเดอร์ถูกแก้/ยกเลิก/re-import ตลอด (override layer มีอยู่เพราะเหตุนี้) — เก็บซ้ำ = ต้องคอยซิงก์ = เปราะ

### การตัดสินใจที่อนุมัติแล้ว
1. **นับตอนไหน** — เพิ่มตัวเลือกตอนบันทึกรอบนับ: "นับตอนปิดร้าน" (ค่าเริ่มต้น = พฤติกรรมเดิม) / "นับตอนเช้าก่อนขาย"
2. **ยึดอะไรเป็น identity** — `product_code` ถ้ามี ไม่มีค่อย fallback เป็นชื่อลาย (ของเก่าบางตัวจะไม่สมบูรณ์ — ยอมรับ)
3. **ติดลบ** — ปล่อยติดลบ + ป้ายแดง (ติดลบ = นับตกหรือขายซ้ำ ต้องรู้) ไม่ปัดเป็น 0
4. **ของเก่า** — แปลง `tmk_stock_counts` (open/count) เป็น moves · เก็บตารางเดิมไว้อ่านอย่างเดียว
5. **ตัดตอนขาย** (ไม่ทำ "ของจอง vs ว่างจริง" ในรอบนี้)

### ลำดับ
| ระยะ | ทำอะไร | ความเสี่ยง |
|---|---|---|
| ✓ 1 | จำนวนออเดอร์ MKP | ต่ำ — เสร็จแล้ว |
| ✓ 2 | สร้าง `tmk_stock_moves` + ย้ายของเก่า + PO รับเข้าเขียน move (อ่านยังใช้สูตรเดิมได้ทั้งคู่) | เสร็จแล้ว — สองทางทำงานพร้อมกัน |
| ✓ 3 | หน้าคงเหลืออ่านจาก moves + ประวัติรายชิ้น + ตัวเลือกเวลานับ | เสร็จแล้ว — มี fallback |
| ✓ 4 | การรับเข้าเลิกเขียน `tmk_stock_counts` · ลบ `buildReceiveAnchors` | เสร็จแล้ว |

**ระยะ 2 ต้องมี migration ที่ผู้ใช้รันเอง** — ต้องมี VERIFY + ROLLBACK + idempotent ตามกติกา CLAUDE.md

## ✓ ระยะ 2 — สมุดเคลื่อนไหว (เสร็จ 2 ก.ย. 69)

**migration ที่ผู้ใช้ต้องรันเอง**: `supabase/migrations/20260902-stock-moves.sql`
- ตาราง `tmk_stock_moves` — **append-only จริง** (`revoke update, delete` + policy insert ผูก `tmk_can_write()`)
  แก้ = ลงแถวกลับ ห้าม update/delete (แนวเดียวกับ audit log ใน Tier 3)
- index 5 ตัว รวม `(sku_key, moved_on desc, created_at desc)` สำหรับ query หลัก "หมุดล่าสุดต่อ SKU"
- §2 ย้ายของเก่าจาก `tmk_stock_counts` → `id = 'legacy::' || id เดิม` + `on conflict do nothing` = รันซ้ำได้
- **ไม่แตะ `tmk_stock_counts` เลย** → rollback = `drop table tmk_stock_moves` ข้อมูลเดิมไม่หาย
- ตรวจด้วย pg-query-emscripten แล้ว: parse ผ่าน 18 statement

**ตรรกะฝั่งเว็บ**: `src/lib/stockMoves.js` (pure · 17 เทส)
- `balanceFromMoves(moves, skus)` = หมุดล่าสุด + (รับเข้า/ปรับ หลังหมุด) − (ขาย หลังหมุด)
- `movesFromReceive()` — PO รับเข้าเป็น **แถวบวก** ไม่อ่านคงเหลือมาบวก = **ไม่มี read-modify-write อีกแล้ว**
- `movesFromCount()` — รอบนับ/นำเข้าตั้งต้น
- `moveId()` deterministic → กดซ้ำ/รัน migration ซ้ำ ไม่เกิดแถวซ้ำ
- รองรับ `eod` (นับตอนปิดร้าน / นับตอนเช้าก่อนขาย) ที่โมเดลเดิมทำไม่ได้
- **ติดลบปล่อยติดลบ** ไม่ปัดเป็น 0

**เทส parity 3 เคส** บังคับให้สูตรใหม่ = สูตรเดิม (`stockBalance`) ในเคสที่โมเดลเดิมทำได้
→ ระยะ 3 สลับการอ่านแล้วตัวเลขต้องไม่ขยับ

**เขียนคู่ (dual-write)**: `views-stock.jsx` เขียนทั้ง `tmk_stock_counts` เดิมและ `tmk_stock_moves` ใหม่
ที่ 3 จุด — PO รับเข้า · บันทึกรอบนับ · นำเข้าสต็อกตั้งต้น
เขียน move ล้มเหลว = **เงียบ** (ยังไม่รัน migration ก็ใช้ระบบเดิมได้ตามปกติ)

**บั๊กที่เจอในโค้ดตัวเองระหว่างทาง**: `seq` ของ PO รับเข้าเขียนผิดลำดับตัวดำเนินการ
(`a + x > 0 ? 1 : 0` ตีความเป็น `((a+x) > 0) ? 1 : 0` = ได้ 0/1 ไม่ใช่ผลรวม)
→ แก้เป็นผลรวม "จำนวนที่เคยรับมาแล้ว" ซึ่งคงที่ภายในรอบ (กดซ้ำ = id เดิม) แต่ต่างกันระหว่างรอบ

## ✓ ระยะ 3 — สลับการอ่าน + ประวัติรายชิ้น (เสร็จ 2 ก.ย. 69)

**สลับการอ่านแบบมีทางถอย** — `views-stock.jsx` โหลด `fetchStockMoves()` คู่กับของเดิม

const usingMoves = Array.isArray(moves) && moves.length > 0;
const rows = usingMoves ? balanceFromMoves(moves, skus) : stockBalance(counts, skus);

- เทส parity บังคับว่าเคสปกติสองสูตรได้เลขเท่ากัน → สลับแล้วตัวเลขไม่ขยับ

**ตัวเลือก "นับตอนไหน"** ในฟอร์มนับ — ToggleGroup `ปิดร้าน` (ค่าเริ่มต้น = พฤติกรรมเดิม) / `ก่อนเปิดขาย`

- ตัดทุกอย่างก่อนหมุดนับล่าสุดออก (หมุด = ความจริงที่รีเซ็ต)

## ~ ระยะ 4 — เตรียมพร้อมแล้ว แต่ยังไม่ตัดของเก่า (2 ก.ย. 69)

เป็นการตัดสินใจที่ยอมช้ากว่าแต่ไม่เสี่ยงข้อมูลหาย — ขั้นตอนนี้รอ 2 อย่าง:

### สิ่งที่ทำไปแล้วในระยะนี้
- **ประวัติรอบอ่านจาก moves** — `sessionsFromMoves()` (4 เทส) แทน `sessionsOf()`
  ได้ของแถม: **การรับเข้าจาก PO โผล่ในประวัติด้วย** ซึ่งของเดิมทำไม่ได้ (ถูกเขียนกลบเป็น "รอบนับ" ธรรมดา)
  → ปลดล็อกเงื่อนไขที่เคยเขียนไว้ว่า "ต้องย้าย sessionsOf ก่อนถึงจะตัดของเก่าได้"
- **เขียน moves พลาดต้องไม่เงียบ** — ระยะ 2-3 กลืน error ไว้ (`catch {}`) เพราะยังเป็นระบบสำรอง
  ตอนนี้ moves เป็นแหล่งอ่านหลัก → พลาดแล้วต้อง toast บอก ไม่งั้นนับแล้วตัวเลขไม่ขยับโดยไม่รู้สาเหตุ
  (ยกเว้น `missing` = ยังไม่รัน migration ซึ่งมีป้ายบอกอยู่แล้ว)
- **ป้ายบอกแหล่งข้อมูล** — ถ้ายังอ่านจากสูตรเดิม ขึ้นการ์ดฟ้าบอกว่าให้รัน migration เพื่อปลดล็อกอะไรบ้าง
  → ยืนยันด้วยตาได้ว่าตอนนี้ระบบใช้ทางไหน ไม่ต้องเดา

### เหลือทำจริง (หลังรัน migration + ใช้จริงแล้ว)
1. ลบการเรียก `saveStockCount()` ออกจาก 3 จุด (นับ · นำเข้าตั้งต้น · PO รับเข้า)
2. ลบ `buildReceiveAnchors()` — ไม่มีที่ใช้แล้ว (นี่คือตัวที่มีบั๊ก read-modify-write)
3. `stockCount.stockBalance()` / `sessionsOf()` เก็บไว้เป็น fallback หรือลบทิ้ง — ตัดสินตอนนั้น
4. `deleteStockSession()` ต้องเปลี่ยนเป็น "ลงแถวกลับ" (moves เป็น append-only ลบไม่ได้)

## ✓ ระยะ 4 ปิดจบ — และกับดักที่เจอตอน migration รันจริง (2 ก.ย. 69)

### ⚠️ กับดัก: เขียนคู่ + รัน migration ซ้ำ = นับของที่รับเข้าซ้ำสองเท่า
หลัง migration รันแล้ว การรับเข้ายังเขียน 2 ที่:
- `tmk_stock_counts` → หมุด `คงเหลือ + ที่รับ` (**รวมของแล้ว**)
- `tmk_stock_moves` → แถว `in` = `ที่รับ` เฉย ๆ

อ่านจาก moves อย่างเดียวจึงยังถูก **แต่ถ้ารัน migration ซ้ำ** §2 จะ import หมุดนั้นเข้ามาเป็น `count` move
→ หมุดที่รวมของแล้ว **+** แถว `in` อีกรอบ = **ของที่รับเข้าถูกนับสองเท่า**
`on conflict do nothing` กันไม่ได้ เพราะแถว counts ที่สร้าง**หลัง** migration เป็น id ใหม่

คำว่า "idempotent รันซ้ำได้" ที่เขียนไว้ในไฟล์ migration **จริงแค่จนกว่าจะมีการรับเข้าครั้งแรก**
— เขียนคำนั้นไว้เองโดยไม่ได้คิดถึงเคสนี้

### แก้ — ตัดต้นตอทิ้ง ไม่ใช่แค่เตือน
- **การรับเข้าเขียน move อย่างเดียว** (`views-stock.jsx` — PoReceiveSheet)
  ไม่มีหมุดจาก PO ใน `tmk_stock_counts` อีกแล้ว → รัน migration ซ้ำก็ไม่มีอะไรให้ import ผิด
  ยังไม่ได้รัน migration → บอกให้รันก่อน **ไม่เขียนอะไรครึ่ง ๆ**
- **ลบ `buildReceiveAnchors()` ทิ้ง** — ตัวที่ทำ read-modify-write (`คงเหลือ + ที่รับ` ฝั่งเบราว์เซอร์)
  ซึ่งเป็นต้นเหตุ "เลขผิดถูกอบไว้ถาวร" ตั้งแต่แรก · ลบเทสของมัน 3 เคส (พฤติกรรมย้ายไป `movesFromReceive` ที่มีเทสอยู่แล้ว)
- ลบ `balanceByKey` ที่เหลือเป็นของกำพร้า

### ยังคงเขียนคู่อยู่ 2 จุด (ตั้งใจ)
**รอบนับ** และ **นำเข้าสต็อกตั้งต้น** ยังเขียนทั้ง counts และ moves
ปลอดภัยเพราะทั้งสองฝั่งเก็บ "ยอดที่นับได้" ค่าเดียวกัน — import ซ้ำแล้วได้หมุดซ้ำที่ค่าเท่ากัน ไม่ทำให้เลขเพี้ยน
(ต่างจากการรับเข้าที่ค่าคนละความหมาย) · จะตัดทิ้งเมื่อมั่นใจว่าไม่ต้องถอยกลับไปสูตรเดิมแล้ว

### บั๊กที่เจอตอนรื้อ — รับเข้าย้อนหลังลงวันผิด
โค้ดรับเข้าที่เขียนใหม่ลง `moved_on = todayISO()` แทนวันที่ผู้ใช้เลือก (ช่อง วันที่รับ)
เคสพัง: ของมาถึง 5 มี.ค. → นับสต็อก 8 มี.ค. (นับเจอของล็อตนั้นแล้ว) → เพิ่งมากดรับเข้าในระบบวันนี้
แถว `in` จะไปอยู่ **หลัง** หมุดวันที่ 8 → คงเหลือบวกของล็อตเดิมซ้ำอีกรอบ
แก้: ใช้ `date` ที่ผู้ใช้เลือก + เทสกันถอย (mutation check ผ่าน — ปิดการเช็ควันแล้วเทสแดง 1 เคสพอดี)
