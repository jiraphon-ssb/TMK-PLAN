# RLS Tier 3 เต็ม — แผนปิดช่องลบข้อมูลตรงจาก browser

สถานะ: **พัก — ยังไม่ลงมือ** (2 ก.ย. 2569)
ผู้ใช้ตัดสินใจว่า "เอาตามเดิมก่อน ยังไม่อยากให้บั๊ก" → **ไม่มีการแก้โค้ดใด ๆ จากแผนนี้**
Stage 0 เคยเขียนไปแล้วรอบหนึ่ง แต่**ถอนออกทั้งหมด**เพราะมันเพิ่มฟังก์ชันที่ยังไม่มีใครเรียก
(+ เทสที่คุมโค้ดซึ่งไม่ถูกรัน) = หนี้ใหม่โดยไม่ได้ประโยชน์วันนี้
เอกสารนี้เก็บไว้เพื่อ **ผลการสำรวจ** — ถ้าจะกลับมาทำ ไม่ต้องไล่ใหม่ตั้งแต่ต้น

## §0 สิ่งที่ตัดสินใจไปแล้ว

| คำถาม | คำตอบ |
|---|---|
| หลังย้ายเข้า RPC แล้ว editor ลบออเดอร์/ใบเสร็จได้ไหม | **ได้เฉพาะของตัวเอง** — RPC เช็คความเป็นเจ้าของ · แอดมินลบได้ทุกใบ |
| §3 "เห็นเฉพาะของตัวเอง" (ใบเสร็จ/คนทัก) | **ยังไม่เอา** — รายงานขายตั้งใจโชว์ยอดทั้งทีม เปิดครึ่งเดียวแล้ว %ปิดเพี้ยน |

## §1 สถานะปัจจุบัน (สำรวจ 2 ก.ย.)

**รันไปแล้ว**
- `BUNDLE-rls-tier3.sql` — เขียน/ลบ = admin/editor · อ่าน = ทุกคนที่ล็อกอิน · audit แก้/ลบไม่ได้
- `20260824-rls-tier3b-narrow.sql` — delete=admin 6 ตาราง · write=admin 4 ตารางเงิน

**ยังไม่รัน**
- `20260811-rls-tier3b-owner-scope.sql` §2 = delete=admin **ทุกตาราง** ← เป้าหมายของแผนนี้

**RPC ที่มีอยู่แล้ว 13 ตัว** — `tmk_delete_orders` · `tmk_void_receipts` · `tmk_restore_receipts` · `tmk_fulfill_order` · `tmk_my_names` · `tmk_can_write` · `tmk_is_admin` ฯลฯ
จุดอันตรายสุด (ลบออเดอร์ยกชุด) ถูกห่อไปแล้ว ใช้แพทเทิร์น **RPC-first + fallback**

## §3 ⛔ Blocker ที่ต้องแก้ก่อน — นิยาม "ของตัวเอง" ไม่ตรงกัน

| | ฝั่งเว็บ `myNamesOf` (`lib/roleAccess.js`) | ฝั่ง DB `tmk_my_names()` |
|---|---|---|
| แหล่งชื่อ | `user.name` + `user.email` | JWT email + `tmk_user_roles.name` + **`tmk_staff.name`** |
| ตัวพิมพ์ | **เทียบตรงตัว** (case-sensitive) | **`lower()` ทั้งหมด** |

ผลถ้าไม่แก้: เว็บซ่อน/โชว์ปุ่มด้วยกติกาหนึ่ง DB ตัดสินด้วยอีกกติกา
→ **ปุ่มโผล่แต่กดแล้วถูกปฏิเสธ** หรือ **ปุ่มหายทั้งที่ลบได้จริง**
เป็นบั๊กที่หายากมากเพราะขึ้นกับว่าชื่อใน 3 ตารางพิมพ์เหมือนกันหรือเปล่า

## §4 แผนลงมือ — 3 ระยะ ไม่ big-bang

### Stage 0 — รวมนิยาม "ของตัวเอง" (ทำก่อน · เล็ก · ปลอดภัย) — ⛔ เคยทำแล้วถอนออก
- `roleAccess.js` เทียบแบบ **case-insensitive** และรวม `staff.name` ให้ตรงกับ DB
- เทสครอบเคสตัวพิมพ์ต่าง / ชื่อจาก staff / ชื่อว่าง / admin
- **ยังไม่แตะ DB** — ฝั่งเว็บอย่างเดียว ไม่มีผลข้างเคียง

### Stage 1 — RPC + ให้เว็บเรียก RPC ก่อน (ยังไม่ล็อกตาราง)
- เขียน RPC 6 ตัว (SECURITY DEFINER · เช็ค `tmk_can_write()` + เจ้าของ + `tmk_is_admin()` ผ่านหมด)
- ทุกตัว **atomic** (ปิดบั๊กเดิมที่ลบครึ่งทางแล้ว "ออเดอร์หายแต่บรรทัดลายค้าง")
- ทุกตัวบันทึก audit
- FE: RPC-first + **คง fallback เดิมไว้** → ถ้า RPC ยังไม่ deploy ระบบยังทำงาน
- ระยะนี้ **ยังไม่มีอะไรพังได้** เพราะสองทางใช้ได้ทั้งคู่

### Stage 2 — ล็อกตาราง (หลังใช้จริงแล้วมั่นใจ)
- migration ตั้ง `delete = admin` ทุกตาราง (restrictive policy)
- ตอนนั้น fallback จะใช้ไม่ได้ = ต้องมั่นใจว่า RPC ครบและถูกทุกเส้นทาง
- มี ROLLBACK block เสมอ

## §5 ความเสี่ยงที่รู้ตัว

- ผู้ใช้ทำงานคนเดียว ไม่มีคนรีวิว → ทุก RPC ต้องมีเทสฝั่ง FE + VERIFY block ฝั่ง SQL
- ออเดอร์ที่ `salesperson` ว่าง (`ไม่ระบุเซลล์`) = ไม่มีเจ้าของ → **เฉพาะแอดมินลบได้**
  ต้องเช็คว่ามี flow ไหนของ editor ที่ต้องลบออเดอร์ไม่มีเซลล์บ้าง (เช่น re-import) ก่อน Stage 2
- `modals-import` ลบก่อน re-import = แตะออเดอร์ของคนอื่นแน่นอน → ต้องเป็น RPC ที่อนุญาต editor ตามขอบเขต "ไฟล์ที่ตัวเองนำเข้า" หรือจำกัดเป็นแอดมิน (ยังไม่ตัดสิน)


## §6 ข้อควรรู้ถ้ากลับมาทำ (บันทึก 2 ก.ย. 69)

- **อย่าเริ่มด้วย Stage 0 แบบเดี่ยว ๆ อีก** — มันไม่เปลี่ยนพฤติกรรมอะไรเลยถ้าไม่มี Stage 1 ต่อ
  (`orderVisibleTo` ที่หน้าจริงใช้อยู่ไม่ได้ถูกแตะ) → ได้แค่โค้ดที่ไม่มีใครเรียก
  ถ้าจะทำ ให้ทำ Stage 0 + Stage 1 ติดกันในรอบเดียว แล้วค่อยหยุดก่อน Stage 2
- **Blocker §3 ยังอยู่** — นิยาม "ของตัวเอง" ฝั่งเว็บกับ DB ยังไม่ตรงกัน (case + แหล่งชื่อ)
  ตราบใดที่ยังไม่ทำ Tier 3 เต็ม มันไม่ก่อบั๊ก เพราะฝั่ง DB ยังไม่ได้ใช้ `tmk_my_names()` ตัดสินการลบ
  แต่**ถ้าวันไหนเปิด owner-scope ต้องแก้ก่อนเสมอ**
- ทางเลือกที่ได้ความปลอดภัยโดยไม่ต้องเขียน RPC เลย: ล็อกเฉพาะกลุ่ม B (6 จุดที่ UI กั้นแอดมินอยู่แล้ว)
  = งานเล็ก ความเสี่ยงต่ำ แต่ปิดช่องได้บางส่วน
